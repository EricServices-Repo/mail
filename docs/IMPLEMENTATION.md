# Security review implementation status

The review at `SECURITY-REVIEW.md` describes commit `502dfc0`. The replacement implementation removes the legacy provisioning model. This document distinguishes implemented controls from acceptance that requires real infrastructure. No production server has been changed or certified by the local implementation work.

## Coverage by finding

- **F01 — implemented:** strict Bash entry points; Python orchestration with checked subprocess exit status and no shell evaluation; root/OS/systemd/SELinux preflight; exclusive operation lock; persistent secrets; deterministic templates; atomic file installation; protected preinstall copies; configuration manifests; management-only ingress until explicit activation. Failed deployment stops affected services and preserves recovery state. Full VM interruption/reboot/rerun testing remains a release gate.
- **F02 — implemented:** unsigned HTTP repositories and direct remote execution removed; DNF package signature enforcement; independently verified offline application digests; archive content validation; content-addressed local runtime bundles; no mutable main/self-download updater. A signed-release packaging script is supplied; initial repository key trust, signing identity and release key custody require operator/repository administration. Archive digests are intentionally not invented or auto-trusted.
- **F03 — implemented:** reviewed minimum application/PHP versions, archive version verification, package inventory, deliberate backup-first application/database upgrades, retained rollback material and documented critical-patch ownership. Version floors must be maintained as advisories change. Compatible complete upstream artifacts and package availability must be verified in the target environment.
- **F04 — implemented:** setup hash consumes the actual random secret over stdin, keeps only the hash, and persists it; blank/wrong password rejection is tested. Web setup is denied permanently; initial administrator provisioning uses a root-only CLI.
- **F05 — implemented:** distinct generated SQL identities; read-only Postfix/Dovecot grants; restricted application runtime grants; root Unix-socket provisioning; prepared SQL values; protected JSON/PHP configuration; no password echo/argv; stable per-install webmail key; restricted ownership/modes. Credentials accepted by text-based daemon grammars are generated hex; arbitrary passwords are never inserted into those grammars. Legacy credential rotation still needs a coordinated migration.
- **F06 — implemented:** loopback-only relay trust including IPv6; submission authenticated independently of mynetworks. Public/LAN/IPv6 relay probe tests are supplied and must run from authorized external sources.
- **F07 — implemented:** explicit master.cf listeners; interoperable public MX with AUTH off; TLS-required authenticated 587; TLS-required IMAPS; modern protocol minimums; verified webmail upstream TLS; unused POP3/143/465 disabled; certificate chain/name/key/expiry checks and renewal deploy hook. Actual network handshake/renewal checks require the target. MTA-STS/DANE are documented deployment extensions requiring DNS/PKI preparation.
- **F08 — implemented:** refuses permissive/disabled SELinux, checks persistent enforcing configuration, installs persistent contexts and narrow documented network booleans; service sandbox drop-ins. No generic audit2allow or global SELinux bypass. Enforcing-mode service behavior remains to be verified on the supported VM.
- **F09 — implemented:** password logging is explicitly disabled; diagnostic auth logging expires after fifteen minutes with a persistent timer; managed config validation rejects secret logging. Historical log exposure/rotation assessment applies to existing deployments.
- **F10 — implemented:** distinct PHP identities, read-only application code, protected pool-owned cache/session/temp directories, restricted PHP endpoints, denied protected/installer routes, HTTPS, client-certificate plus CIDR restricted administration, enabled TOTP, stronger portal password policy, session/upload controls and security headers. Operators must enroll/verify TOTP and implement their client-certificate revocation/short-lived-certificate policy. Optional legacy fetchmail, vacation and domain-alias features are disabled rather than exposing unsupported paths.
- **F11 — implemented:** valid literal PHP templates, cryptographically random 24-byte webmail key, JSON/DSN serialization, protected fixed TLS endpoints, CLI database initialization/migration and disabled/removed web installer. Local PHP lint and setup hash tests pass; full webmail/attachment/session tests need staging.
- **F12 — implemented:** validated domain CLI using prepared SQL and idempotent domain records; stable service hostnames and certificate lineage; per-domain DKIM keys/DNS output; no whitelist or ad hoc vhost/SAN mutation. Domain changes go through reviewed desired state; the administrative UI must not be used to create untracked domains without provisioning their keys/DNS. External multi-domain mail and DNS tests remain required.
- **F13 — implemented:** incoming/outgoing Rspamd milters; temporary deferral on filter failure; account recipient-rate buckets; DKIM signing; default SPF/DKIM/DMARC evaluation; envelope ownership plus authenticated MIME From binding; Dovecot quotas; Postfix connection/recipient/queue/storage bounds; Fail2ban; auth/abuse-spike health alerts. DNSBL access/terms, DNS records, policy tuning, external synthetic probes and any required antivirus integration need site-specific setup. Domain aliases and automatic delegated/multi-recipient send-as are deliberately unsupported.
- **F14 — implemented by removing unsafe feature:** both replication helpers fail explicitly; MariaDB has no network listener; backups/recovery are the supported baseline. Multi-node replication/fencing is not claimed or silently provisioned.
- **F15 — implemented:** mandatory initialized encrypted offsite Restic repository; coordinated writer pause/database dump; protected configuration/key/mail recovery set; service restart on failures; systemd timeout/recovery hook; snapshot verification; isolated verified restore target; backup freshness/storage/queue/TLS/service monitoring; bounded journal logs; independent notification hook; documented external canary, retention and restore drills. Real offsite success, notification delivery, restore outcomes, RPO/RTO and upstream durable queuing must be measured. Snapshot extraction alone does not certify recovery.
- **F16 — implemented:** one supported OS/component target; no broad distribution claim; supported account-management SQL; fully scoped Dovecot service blocks; actual installed-daemon validators; manually dispatched disposable-VM workflow. The full VM workflow has not been run in this local macOS workspace.

## Tests and release boundary

Run `tests/check.sh` for ShellCheck, shell syntax, generated PHP lint and unit/security regression tests. The suite tests malformed/injected configuration, signature/digest boundary behavior, unsafe archives, secret-file permissions, nonreused identities, setup hash correctness, deterministic output, native PHP/Nginx variable preservation, listener policy, publication gates and service recovery on backup failure.

`tests/vm-acceptance.sh` requires an explicitly acknowledged disposable Rocky lab with external prerequisites. It installs/reruns and checks actual daemon configuration under enforcing SELinux. `tests/probe.py` checks authorized external SMTP/IMAP boundaries and optional controlled test delivery. Neither script manufactures passing evidence for unrun restore, upgrade, reboot, failure-injection or DNS tests.

Release evidence binds both the configuration fingerprint and installed content-addressed runtime release. All configured production gates must be true and recent before public activation. The evidence is an operator attestation with separately retained results, not a substitute for executing the checks.
